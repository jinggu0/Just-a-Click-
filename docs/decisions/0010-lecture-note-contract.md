# 0010 — 강의 초안·노트 출력 계약

- 날짜: 2026-09-26
- 상태: 계약 v2(작업 나누기) 채택(2026-09-26). v1은 채택 보류였다. 시간은 배경 부하를 줄인 재측정(2026-09-27)에서 창·녹음 종료 후 기준 모두 통과
- 근거 측정: [v1 실측](../validation/2026-09-26-lecture-contract.md), [v2 실측](../validation/2026-09-26-lecture-contract-v2.md), [시간 재측정](../validation/2026-09-26-lecture-contract-timing.md), [시간 재측정 2](../validation/2026-09-27-lecture-contract-timing-2.md), [v1 설계](../superpowers/specs/2026-09-25-lecture-note-contract-design.md), [v2 설계](../superpowers/specs/2026-09-26-lecture-contract-split-design.md)
- 관련 결정: [0005](0005-summary-contract.md) 회의 계약, [0006](0006-lecture-first-product-scope.md) 제품 범위·5분 노트, [0007](0007-app-stack.md) 앱 구조, [0009](0009-concurrent-processing.md) 동시 처리

## 1. 결정

**강의 요약 계약은 섹션별 타입 스키마로 두고, 모델은 내용만 쓰며 전사로 정할 수 있는 것은 앱이 정한다.** 녹음 중 5분 창마다 만드는 구간 초안(`lecture-draft-v1`)과 녹음 후 만드는 강의 노트(`lecture-note-v1`) 두 계약을 `schemas/`에 두고, 앱의 `contract.rs`·`lecture.rs`가 검증한다. 파이썬 회의 계약(0005)은 그대로 둔다.

| 항목 | 결정 |
| --- | --- |
| 초안 섹션 | 요점 1~8, 개념 이름 0~8, 예제 0~6, 코드 0~8, 공지 0~5 |
| 노트 섹션 | 주제, 개념 1~20, 예제 0~15, 용어 0~20, 공지 0~10, 코드 0~20, 복습 0~10 |
| 출처 | 모든 항목이 입력 구간 ID를 1개 이상, 중복 없이 인용한다. 생성 때 구간 ID를 `enum`으로 제약한다 |
| 앱이 채우는 값 | 초안의 창 범위, 코드가 인용 구간에 그대로 있는지(아니면 "복원·확인 필요"), 영문 원어가 인용 구간에 있는지(아니면 "모델 보강"). 모델이 이 값을 쓰면 거부한다 |
| 앱의 정리 | 인용 구간에 없는 날짜·범위와 채움 문자열은 `null`("확인 필요"), 채움 항목·똑같은 반복·정의가 용어를 되풀이한 용어는 삭제. 정리는 모두 기록하고 새 값을 만들지 않는다 |
| 거부 | 잘림, 문법·구조 오류, 중복 키, 출처 오류, 필수 섹션 비움, 항목 수 초과. 위반 목록을 붙여 1회만 재시도하고, 두 번 실패하면 완료로 저장하지 않는다 |

## 2. 채택 보류 이유

합성 강의 5회 측정(AC·"최고 성능")에서 25건이 모두 구조·출처 검사를 통과했지만, 설계의 채택 기준을 채우지 못했다.

- 창작 방지 기대치 "모호한 기한은 `null`"이 정밀 정리 5건 중 4건에서 깨졌다. "다음 주쯤"처럼 전사에 그대로 있는 모호한 표현이 날짜로 들어가 원문 대조로 걸러지지 않았다.
- 초안 15건 모두 개념·예제·코드가 비고 내용이 요점으로만 갔다. 노트 10건에도 코드가 없었다.
- 취소된 퀴즈를 날짜가 붙은 시험으로 분류했고, 없는 과제를 만들었으며, 같은 공지를 되풀이했다.

## 3. 시간 영향 (결정 0009 가정)

- 초안 출력은 최대 557토큰으로 0009의 300토큰 가정의 1.9배였다. 시간은 최대 107.3초로 창 초안 기준(150초) 안이었다.
- 초안으로 노트 전체를 모델이 다시 쓰는 5분 노트 경로는 녹음 종료 후 추정이 236~1,563초로 5회 중 2회가 300초를 넘었다. 5분 노트는 0006대로 앱 병합 위주로 만들어야 하며, 이는 작업 4에서 정한다.

## 4. 다음 결정

계약 v1 구조는 유지하고 다음 가운데 무엇을 먼저 할지 정한다. 어느 쪽이든 같은 합성 강의와 실제 강의로 다시 측정한다.

1. 작업 나누기: 초안은 요점과 근거만, 공지·코드는 전용 호출이나 규칙 기반 후보 추출로 모은다.
2. 5분 노트를 앱 병합으로 만들고 모델은 주제·복습 같은 합성 부분만 쓴다(작업 4).
3. 같은 공지 반복 제거 같은 결정적 정리를 더한다.
4. 구조를 바꾼 뒤에도 부족하면 [LLM 지역화](../LLM-SPECIALIZATION.md)의 지도 미세조정 근거로 쓴다.

## 5. 한계

- 합성 강의 1개, 5회 반복이다. 기대치는 fixture 전용 회귀 검사이며 의미 충실성은 자동 채점하지 않았다.
- 계약의 일부 규칙은 같은 합성 강의로 시험한 뒤 정했으므로 과적합 가능성이 있다.
- 실제 강의 녹음·전사 오류, 2~3시간 분량, RAM 16GB 기기는 미검증이다.

## 6. v2: 작업 나누기 (2026-09-26)

**4절의 다음 결정 1을 적용한 계약 v2를 채택한다.** 창마다 요점(`lecture-points-v1`)·공지(`lecture-notices-v1`)·코드(`lecture-code-v1`)를 따로 호출하고, 노트는 모델이 본문(`lecture-note-body-v1`: 주제·개념·예제·용어·복습)만 쓰며 공지·코드는 앱이 초안에서 합친다(`lecture-draft-v2`, `lecture-note-v2`). 1절의 역할 분담과 정리 규칙은 그대로이고 다음을 더했다.

| 추가 규칙 | 내용 |
| --- | --- |
| 날짜 형태 | `date_text`에 숫자+월·일·시나 요일이 없으면 `null`("다음 주쯤", "잠깐", "내일") |
| 공지 상태 | `status`(`scheduled`·`cancelled`). llama-server가 키를 알파벳 순서로 생성하므로 판단 필드는 내용 뒤에 오는 이름을 쓴다 |
| 코드 정리 | 영문자·숫자가 없는 코드 항목 삭제 |
| 병합 | 여러 초안의 같은 공지(종류·내용이 같거나 같은 구간의 같은 날짜)와 같은 코드는 하나만 남기고 기록 |

합성 강의 5회(AC·"최고 성능")에서 호출 75건이 재시도 없이 모두 채택됐고 판정용 기대치 7개가 5회 모두 통과했다. v1에서 실패한 모호한 기한(11/15→15/15), 코드 누락(0/15→15/15), 취소된 퀴즈 분류, 쉬는 시간 발언의 가짜 공지가 모두 해결됐다.

**시간은 재측정으로 판정했다(통과).** v2 측정에서는 창 최대 212초(150초 기준 초과 5/15), 녹음 종료 후 추정 429~622초로 기준을 넘었다. 그러나 생성 속도가 초당 6.7토큰으로 측정 직전 시험(12.9토큰)의 절반이었고 원인(충전 중 전력 제한, 발열 등)을 확인하지 못했다. 시험 속도로 환산하면 창 약 76초, 녹음 종료 후 약 240초다(추정). 창 하나의 출력은 세 호출 합 약 880토큰으로 0009의 300토큰 가정보다 크다. 배터리를 채운 AC 상태에서 전력·온도를 함께 기록해 다시 쟀다([시간 재측정](../validation/2026-09-26-lecture-contract-timing.md)). 생성 속도는 10.5토큰/초로 유지됐고 창은 15/15가 150초 안(최대 93.7초)이었지만, 녹음 종료 후 추정은 5회 중 1회가 320초로 기준을 넘었다. 패키지 전력이 약 20W로 일정해 GPU와 CPU 코어가 이 예산을 나눠 쓰며, 측정 중 배경 CPU 부하(OneDrive·검색 색인, 사용률 중앙값 83%)가 컸다. OneDrive를 멈추고 다시 잰 결과([시간 재측정 2](../validation/2026-09-27-lecture-contract-timing-2.md)) 생성 속도는 13.0토큰/초, 창 최대 76.9초(15/15), 녹음 종료 후 추정 199~249초(5/5)로 **시간 기준을 통과했다**. 판정용 기대치도 5회 모두 통과했다. 배경 CPU 부하가 있으면 녹음 종료 후 추정이 기준 근처까지 오르므로 실제 강의 측정(작업 4)에서도 부하를 기록한다. 첫 재측정에서는 정밀 정리 1건의 `topic`이 모든 구간을 인용해 잡담 기대치가 깨졌다(24/25).

남은 품질 문제는 판정 대상이 아니므로 기록만 한다: 코드 호출에 섞이는 영문 개념 이름("Banker's algorithm", "C"), 틀린 영문 보강("타조 알고리즘=Duck algorithm"), 정밀 정리의 용어 이름 반복.
