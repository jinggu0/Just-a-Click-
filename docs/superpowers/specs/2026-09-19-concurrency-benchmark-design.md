# 녹음 중 STT·LLM 동시 실행 측정 설계

- 날짜: 2026-09-19
- 상태: 사용자 승인 설계. 구현·측정 전
- 대상 작업: [로드맵](../../ROADMAP.md) M0 남은 작업 3. 녹음 중 STT와 LLM 동시 실행의 속도·메모리·배터리, RAM 16GB 가능 여부, 순차 모드 전환 조건
- 판정 조건: AC 전원·Windows 전원 모드 "최고 성능"([결정 0006](../../decisions/0006-lecture-first-product-scope.md) 3절). 다른 전원 조건은 참고로 기록한다
- 선행 결과: [STT 측정](../../validation/2026-09-18-stt-bench.md)(1차 후보 large-v3-turbo f16, OpenBLAS·8스레드, 조각 RTF 중앙값 0.422, 코어 약 6개 사용), [LLM 재측정](../../validation/2026-09-17-llama-bench-best-performance.md)(Vulkan, 스레드 4·FA off, 5분 창 초안 24.5~26.3초 추정)

## 1. 목적과 범위

기준 노트북에서 실제 강의 녹음처럼 STT와 LLM을 함께 실행해 다음을 1차 판정한다.

1. 녹음 중 STT가 녹음 속도를 따라가면서 LLM이 5분 창마다 구간 초안을 만들 수 있는가.
2. 동시 실행의 메모리 사용량으로 RAM 16GB 노트북에서 가능한지(추정).
3. 2시간 연속 처리의 발열·전력과, 참고 조건(최고의 전원 효율성·배터리)의 동작·배터리 소모.
4. 순차 모드(녹음 중 전사만 수행)로 바꿀 조건.

범위 밖: 실제 강의 녹음, 초안 내용의 품질, 오디오 캡처, 온라인 강의 재생 부하, 16GB 실기기 측정, GPU·NPU STT, 앱 구현.

## 2. 사용자 결정 사항

| 항목 | 결정 |
| --- | --- |
| 측정 범위 | 판정 조건(AC·최고 성능) 2시간 연속과 참고 조건(AC·최고의 전원 효율성 30분, 배터리·최고 성능 최대 1시간, 배터리 30%에서 중단). 여러 번에 나눠 실행할 수 있다 |
| 스레드 배분 | 2시간 측정 전에 배분 3가지를 10분씩 비교해 고른다 |
| 접근 방식 | 실시간 재현. 음성 조각을 녹음 속도로 도착시키고 STT·LLM을 동시에 처리한다. `whisper-server`는 인증·출처 제한이 없고 모델 적재 경로가 있어 STT 설계에 이어 쓰지 않는다 |
| 16GB 추정 기준 | 공유 GPU 메모리 한도(물리 메모리의 절반)와 동시 실행 합계 12GiB(16GB에서 OS·다른 앱 몫 4GiB를 뺀 가정) |
| 전원 설정 | 조건마다 사용자가 전원 모드·전원 연결을 바꾼다. 측정 도구는 읽기만 한다 |

## 3. 판정 기준

모든 판정은 추정이며 앱의 실제 지연시간이나 출시 품질 판정이 아니다.

- **전사 지연:** 조각의 녹음이 끝난 시각(도착 시각)부터 그 조각의 전사가 끝난 시각까지다. 대기 시간과 모델 적재 시간을 포함한다.
- **전사 추종:** 전사 지연의 95번째 백분위(최근접 순위) ≤ 30초이고 최대 ≤ 60초다. 60분 이상 측정에서는 마지막 30분의 지연 중앙값이 처음 30분보다 10초 넘게 늘지 않아야 한다(대기열 누적 없음).
- **구간 초안:** 초안 1건의 시간(요청부터 응답까지, 앞 요청 대기 제외)의 최대 ≤ 150초다. 이는 5분 창의 점유율 0.5에 해당한다.
- **녹음 종료 후 5분 재추정:** 판정 측정의 초안 시간 최대 × 2(남은 창) + 최종 통합 40.3초 ≤ 300초. 최종 통합 시간은 LLM 재측정의 추정(녹음 종료 후 89.3초 − 창 24.5초 × 2)을 쓴다.
- **16GB 메모리(추정):** 다음 두 조건을 모두 만족해야 한다.
  - llama-server의 GPU 공유 메모리 최대 ≤ 16GB 기기의 공유 GPU 메모리 한도(물리 메모리의 절반, 약 7.8GiB).
  - STT 조각별 최대 전용 메모리 + llama-server 전용 메모리 최대 + GPU 공유 메모리 최대 ≤ 12GiB. llama-server의 전용 메모리에 GPU 공유 메모리가 함께 잡히는지는 메모리 확인 단계에서 점검하고, 겹치면 합계에서 한 번만 센다.
- **대기 모드 의심:** 카운터 기록 사이에 60초 넘는 공백이 있으면 해당 측정을 판정 불가로 둔다.
- **스레드 배분 선택:** 전사 추종을 만족한 배분 중 초안 시간 중앙값이 가장 낮은 배분을 고른다. 차이가 10% 이내면 전사 지연 95번째 백분위가 낮은 배분을 고른다. 만족한 배분이 없으면 2시간 측정 전에 사용자에게 보고하고 결정을 받는다.
- **기록만 하는 항목:** 온도 중앙값·최대, 열 제한(`% Passive Limit` < 100) 발생, 패키지 전력, 배터리 방전율(W)과 시간당 소모(%/h), 예상 지속 시간, 조각 CER.
- **순차 모드 전환 조건:** 측정값으로 결정 기록 초안에 제안한다(예: 전사 지연 60초 초과가 연속될 때, 가용 메모리가 일정 수준 아래일 때, 배터리 사용 중).

## 4. 입력과 부하

- **음성:** STT 측정의 조각 목록 `stt-fleurs-ko-v1`(조각 60개, 1,406초)을 순서대로 반복한다. 2시간은 약 5.1회다. 마지막 반복은 필요한 길이만큼만 쓴다.
- **도착:** 조각 i는 "측정 시작 + 조각 1~i의 음성 길이 합"에 도착해 STT 대기열에 들어간다.
- **STT:** large-v3-turbo f16, OpenBLAS 빌드, `-nt -l ko`, 배분에 따른 스레드 수. 조각마다 `whisper-cli`를 실행하고 시간 제한은 300초다(STT 측정과 같은 방식).
- **LLM 창:** 전사가 끝난 조각의 음성 길이 합이 300초 이상이 되면 창을 닫고, 그 조각들의 전사문을 이어 붙여 초안 요청 1건을 보낸다. 실패한 조각은 빠진다. 앞 요청이 진행 중이면 대기한다.
- **LLM 요청:** llama-server(`b10994` Vulkan, `-ngl 99`, 컨텍스트 8,192, `-np 1`, FA off, `-b 2048 -ub 512`, `--reasoning off`, 127.0.0.1, 임의 포트, 환경 변수로만 전달하는 임의 인증 토큰)에 `/v1/chat/completions`로 보낸다. 요청 조건은 구간 초안 지시문(요점, 개념·용어, 예제, 공지 후보) + 전사문, `max_tokens` 300, `ignore_eos`, `temperature` 0, `seed` 42, `cache_prompt` false다. 출력 300토큰 고정은 결정 0006의 구간 출력 가정과 같다. 초안 내용은 평가하지 않는다.
- **녹음 종료 처리:** 마지막 조각이 도착하면 남은 전사를 마치고 마지막 부분 창을 초안으로 만든다. 이 구간의 시간은 "종료 후 처리"로 따로 기록한다.

## 5. 실행 흐름

1. **사전 점검:** 모델·빌드 크기·해시, 조각 WAV, 경쟁 추론 프로세스, AC 연결(참고 조건은 `--allow-battery`), 전원 모드(경고·기록)를 확인한다. 측정 중에는 절전과 화면 꺼짐 방지를 요청한다.
2. **메모리 확인(`probe`):** 컨텍스트 4,096·8,192·16,384로 서버를 각각 띄워 짧은 요청 1건 뒤 전용 메모리와 GPU 공유 메모리를 기록하고 종료한다. whisper-cli로 조각 1개를 실행해 STT 최대 메모리도 기록한다. 약 5분이다.
3. **스레드 배분 비교(`screen`, AC·최고 성능):** STT 8·LLM 4, STT 8·LLM 2, STT 6·LLM 2를 10분씩(창 2개) 실행한다. 배분마다 서버를 다시 띄우고 짧은 예열 요청 1건은 통계에서 뺀다. 3절 규칙으로 배분을 고른다.
4. **판정 측정(`run`, AC·최고 성능):** 고른 배분으로 120분 실행한다.
5. **참고 측정(`run`):** AC·최고의 전원 효율성 30분, 배터리·최고 성능 60분(잔량 30% 이하에서 새 도착 중단)을 실행한다. 조건 이름은 전원 상태와 모드에서 자동으로 붙인다(예: `ac-best_performance`).
6. **요약:** 단계·조건마다 요약 JSON과 표를 쓴다.

`--minutes`를 기본값보다 짧게 주거나 `--diagnostic`을 쓴 실행은 진단용으로 보고 결과를 `artifacts/`에만 남긴다.

## 7. 기록

- **조각:** 도착·시작·끝 시각, 전사 지연, 처리 시간, RTF, CER, whisper 최대 작업 집합·전용 메모리, 상태.
- **창:** 창을 닫은 시각, 요청 시각(대기 시간), 입력 조각 수·음성 길이, 입력 토큰, 입력 처리·생성 시간과 속도(서버 `timings`), 전체 시간, 상태.
- **llama-server:** 1분마다 현재 작업 집합·전용 메모리, 프로세스별 GPU 공유 메모리. 시작 시간과 컨텍스트·스레드 설정.
- **카운터(5초):** 전체 CPU, 프로세서 성능, 온도, `% Passive Limit`, 패키지·코어·GPU 전력, 가용 메모리, 커밋 바이트, GPU 어댑터 공유 메모리, 배터리 방전율(mW)·잔량(mWh), whisper-cli·llama-server·탐색기·검색 색인 CPU.
- **환경:** 시작·종료 시 전원 상태·모드, 배경 부하 스냅샷.
- 조각 전사 원출력, 서버 로그, 카운터 CSV는 `artifacts/concurrency-<ns>/`에 둔다. 요약은 조각·창이 끝날 때마다 `artifacts/`에 다시 저장해 중간에 멈춰도 보존한다. 커밋하는 요약에는 전사·초안 전문과 로컬 경로를 남기지 않는다. 결과 파일은 덮어쓰지 않는다.

## 8. 오류 처리

- 조각 실패·시간 초과(300초)는 기록하고 계속한다. 초안 요청 실패·시간 초과(600초)도 기록하고 다음 창으로 넘어간다.
- llama-server가 종료되면 측정을 실패로 끝내고 서버 로그의 마지막 줄을 경로를 가려 요약에 남긴다.
- 사전 점검에 실패하면 시작하지 않는다(파일 불일치, 경쟁 프로세스, AC 미연결).
- 카운터 공백 60초 초과는 대기 모드 의심으로 표시하고 판정 불가로 둔다.
- 전원 설정·드라이버를 바꾸지 않는다. OneDrive 등 사용자 앱은 허락을 받은 경우에만 종료하고 측정 후 다시 실행한다.

## 9. 검증

- 단위 테스트: 도착 스케줄(가짜 시계), 전사 지연·추종 판정(누적 포함), 창 경계(300초 누적·실패 조각 제외·마지막 부분 창), 초안 통계, 종료 후 5분 재추정, 16GB 메모리 예산, 배터리 소모율, 배분 선택 규칙, 서버 명령 구성(127.0.0.1, 토큰이 명령줄에 없음), 요청 본문(`max_tokens` 300, `ignore_eos`), 경로 가림, 프로세스 메모리 조회, `run_chunk`의 최대 메모리 기록. 기존 테스트도 계속 통과한다.
- 실제 실행 확인: 측정 전에 5분짜리 진단 실행(창 1개)으로 STT·LLM 동시 처리, 기록, 카운터 수집을 확인한다.
- 측정 후 보고서를 작성하고 로드맵 M0 남은 작업 3과 결정 기록 초안에 반영한다.

## 10. 후속 작업

- RAM 16GB 실기기에서 같은 도구로 동시 실행을 확인한다.
- 강의 녹음 확보 후 실제 발화 속도·구간 토큰 수로 창 크기와 출력량을 조정한다.
- 온라인 강의 재생(시스템 소리 녹음) 부하를 함께 건 측정을 검토한다.
- 동시 실행이 부족하면 순차 모드, 컨텍스트 축소, 스레드 조정, GPU·NPU STT 경로를 사용자 결정으로 검토한다.
