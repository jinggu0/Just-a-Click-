# 앱 기술 검증 2차 설계: 추론 프로세스·한국어 검색·자격 증명

- 날짜: 2026-09-25
- 상태: 사용자 승인 설계. 구현·검증 전
- 대상 작업: [로드맵](../../ROADMAP.md) M0 남은 작업 7 중 [결정 0007](../../decisions/0007-app-stack.md) 3절의 ③(추론 프로세스 시작·종료·장애 복구·작업 취소), ④(SQLite FTS5 한국어 부분 일치 검색), ⑤(Windows 자격 증명 관리자 토큰 저장·삭제)
- 1차 결과: [앱 기술 검증 1차 보고서](../../validation/2026-09-25-app-stack.md), [1차 설계](2026-09-23-app-stack-validation-design.md)

## 1. 목적과 범위

기준 노트북의 Tauri 2 앱이 다음을 할 수 있는지 확인한다.

1. 추론 런타임(llama-server, whisper-cli)을 별도 프로세스로 띄우고, 인증·취소·강제 종료 복구·앱 종료 시 정리까지 다룬다.
2. 강의 100개 규모의 한국어 전사·노트에서 부분 일치 검색이 쓸 만한 속도로 동작한다.
3. Notion 내부 연결 토큰을 Windows 자격 증명 관리자에 저장하고 삭제한다.

범위 밖: 실제 요약 품질과 프롬프트, 라이브러리 화면 디자인, 데이터 스키마 확정과 마이그레이션(로드맵 남은 작업 10), Notion 실제 전송(B 단계), Windows 10 확인, RAM 16GB 실기기 확인.

## 2. 사용자 결정 사항

| 항목 | 결정 |
| --- | --- |
| 산출물 깊이 | 1차와 같은 검증 골격. `app/`에 모듈과 검증 탭을 더하고 자동 테스트·측정으로 판정한다 |
| ③ 범위 | llama-server와 whisper-cli 모두. 시작·준비 대기·요청·취소·정지에 더해 강제 종료 복구와 앱 종료 시 고아 방지까지 확인한다 |
| ④ 규모 | 강의 100개·2시간분 코퍼스에서 trigram·unicode61·LIKE 세 방식을 비교한다. 판정은 질의 종류별 재현율 중심이며 지연 95번째 백분위 300ms는 하한으로 둔다(4절 ④의 "판정 기준을 바꾼 이유") |
| ⑤ 구현 | `keyring` 크레이트 대신 `windows` 크레이트의 자격 증명 API를 직접 호출한다 |
| 고아 방지 | Job Object(`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`)와 정상 종료 경로의 순차 정지를 함께 쓴다 |
| HTTP 호출 | 의존성 트리에 이미 있는 `reqwest`를 쓰고 새 HTTP 크레이트를 넣지 않는다 |
| 데이터베이스 | `rusqlite`의 `bundled` 기능으로 SQLite를 동봉해 버전을 고정한다 |

## 3. 확인한 사전 조건 (2026-09-25)

- 앱의 의존성 트리에 `reqwest` 0.13.5, `tokio` 1.53.1, `hyper` 1.11.1이 이미 들어 있다(Tauri 2.11.6이 끌어온다). 루프백 HTTP 호출에 새 크레이트가 필요 없다.
- `windows` 0.62.2도 이미 트리에 있다. 자격 증명 관리자(`Win32::Security::Credentials`)와 Job Object(`Win32::System::JobObjects`)를 같은 크레이트에서 쓸 수 있다.
- 크레이트 조사(crates.io API): `rusqlite` 0.40.2(MIT, 2026-08-08 갱신), `keyring` 4.2.0(MIT OR Apache-2.0, 2026-08-29 갱신). ⑤는 의존성을 늘리지 않으려고 `keyring`을 쓰지 않는다.
- FTS5의 trigram 토크나이저는 SQLite 3.34 이상에서만 있다. `rusqlite`의 `bundled`가 어떤 버전을 담는지는 검증 첫 단계에서 `sqlite_version()`으로 확인한다.
- 런타임과 모델은 이미 기기에 있다: `runtimes/b10994/vulkan/llama-server.exe`, `runtimes/whisper-b5130/blas/Release/whisper-cli.exe`, `models/Qwen3-8B-Q5_K_M.gguf`, `models/whisper/ggml-large-v3-turbo.bin`.
- 실행 설정은 [결정 0009](../../decisions/0009-concurrent-processing.md)를 따른다: 컨텍스트 8,192, `-np 1`, 프롬프트 캐시 끔, 전 계층 GPU, LLM 2스레드, STT 8스레드.
- 코퍼스 재료는 이미 내려받은 FLEURS 한국어 시험 문장 382개(23,888자, CC BY 4.0)다. `downloads/`는 추적하지 않는다.
- STT 취소 시험 입력은 1차 검증에서 만든 30초 조각을 그대로 쓴다(`artifacts/app-recordings/`, 커밋하지 않는다).
- 기존 `scripts/llm_server.py`가 같은 일을 파이썬으로 한다. 토큰을 환경 변수로 넘기고 빈 포트를 먼저 잡는 방식을 그대로 옮긴다.

## 4. 성공 기준

### ③ 추론 프로세스

| 항목 | 기준 |
| --- | --- |
| 서버 시작 | `/health`가 준비를 알릴 때까지 300초 이내. 준비까지 걸린 시간을 기록한다 |
| 인증 | 토큰 없는 요청과 틀린 토큰 요청은 401, 올바른 토큰은 200 |
| 노출 범위 | 기기의 LAN 주소로 같은 포트에 연결하면 실패한다 |
| 생성 취소 | 300토큰 생성 중 취소하면 앱 쪽 작업이 2초 이내에 끝나고, 같은 서버로 보낸 다음 요청이 정상 응답한다 |
| 전사 실행 | 30초 조각 전사가 성공하고 결과에 한국어 텍스트가 들어 있다 |
| 전사 취소 | 취소 후 5초 이내에 자식 프로세스가 사라지고 부분 출력 파일이 남지 않는다 |
| 장애 복구 | 서버를 밖에서 강제 종료하면 상태가 `failed`가 되고, 재시작 명령으로 다시 준비 상태가 된다 |
| 고아 방지 | 하네스를 `taskkill /F`로 죽인 뒤 `llama-server`·`whisper-cli` 프로세스가 0개다 |
| 정상 정지 | 정지 요청 5초 이내에 자식이 종료된다 |
| 메모리 | 시작·요청 중·정지 후 3회 기록하고 결정 0009의 16GB 예산과 비교한다 |

### ④ 한국어 부분 일치 검색

| 항목 | 기준 |
| --- | --- |
| 사전 확인 | `sqlite_version()`을 기록하고 trigram 가상 테이블 생성이 성공한다 |
| 코퍼스 | 강의 100개 × 약 4만 자(합계 약 400만 자). 강의마다 고유 용어 20개를 섞어 선택도가 다른 질의를 만든다 |
| 비교 대상 | FTS5 trigram, FTS5 unicode61, `LIKE '%…%'` 세 가지 |
| 질의 | 코퍼스에서 다섯 종류를 뽑는다: 조사가 붙은 어절의 어간, 어절 중간의 부분 문자열, 두 글자 단어, 영문, 강의 고유 용어 |
| 정답 | 본문을 그대로 부분 문자열로 대조해 만든다. 어느 검색 엔진의 결과도 정답으로 쓰지 않는다 |
| 부분 일치 | 방식별로 질의 종류마다 재현율(상한 20건 기준)과 정확도를 잰다. 판정은 모든 종류에서 재현율 1.0을 내는 방식 또는 조합을 찾는 것이다 |
| 지연 | 질의마다 10회 실행해 중앙값·최대를 기록한다. 95번째 백분위 300ms 이내는 하한 조건이다 |
| 색인 | 방식별 색인 시간과 DB 파일 크기를 기록하고 원문 대비 배수를 남긴다 |

**판정 기준을 바꾼 이유(2026-09-25, 실행 계획 작성 중 확인).** 처음 기준은 "조사·어미가 붙은 질의 20개를 모두 찾는다"와 "trigram 95번째 백분위 300ms"였다. 스파이크로 확인해 보니 두 기준 모두 판정에 쓸 수 없었다. 부분 일치 검색은 질의 문자열 전체를 본문에서 찾으므로, 본문이 "확률변수의"일 때 "확률변수를"로 검색하면 어떤 방식도 찾지 못한다. 실제로 필요한 것은 본문에 조사가 붙어 있고 사용자가 어간을 입력하는 경우다. 또 400만 자 코퍼스에서 세 방식 모두 36ms 안에 답해 속도로는 방식을 가를 수 없었다. 반면 질의 종류에 따라 결과가 크게 갈렸다. trigram은 두 글자 질의를 하나도 찾지 못했고, unicode61은 어절 중간 부분 문자열과 조사가 붙은 고유 용어를 찾지 못했다. 그래서 판정을 질의 종류별 재현율로 바꾸고 300ms는 하한으로만 둔다.

### ⑤ 자격 증명

| 항목 | 기준 |
| --- | --- |
| 저장·조회 | 저장한 토큰이 그대로 조회된다 |
| 지속 | 하네스를 다시 실행해도 조회된다 |
| 삭제 | 삭제 후 조회 결과가 "없음"이고 `cmdkey /list`에도 항목이 없다 |
| 누출 | 하네스 로그·설정 파일·검증용 DB에서 토큰 문자열이 검색되지 않는다 |
| 이름 규칙 | 항목 이름은 `dev.justaclick/<용도>`를 쓰고, 검증에서는 `dev.justaclick.test/notion`만 건드린다 |

## 5. 앱 모듈과 구조

```
app/src-tauri/src/
  process.rs   Job Object 생성과 자식 프로세스 시작·정지
  llm.rs       llama-server 시작·준비 대기·요청·취소
  stt.rs       whisper-cli 실행·취소·결과 읽기
  store.rs     SQLite 연결·검증용 스키마·적재
  search.rs    세 가지 방식의 질의
  secrets.rs   자격 증명 관리자 저장·조회·삭제
app/src-tauri/examples/
  inference_check.rs  ③ 절차를 순서대로 실행하고 JSON으로 결과를 남긴다
  search_bench.rs     ④ 코퍼스 생성·색인·질의 측정을 실행한다
```

- `process.rs`는 OS 경계만 맡는다. Job Object를 만들고 자식을 등록해, 하네스나 앱이 어떤 이유로 죽어도 커널이 자식을 정리하게 한다. 정상 경로에서는 종료 요청 후 5초를 기다리고 남으면 강제 종료한다.
- `llm.rs`는 빈 포트를 먼저 잡고 토큰을 만들어 환경 변수로 넘긴다. 준비 대기, 요청, 취소만 노출하고 프로세스 생성은 `process.rs`에 맡긴다.
- `stt.rs`는 `whisper-cli`를 조각 파일 하나에 대해 실행하고, 취소 시 자식을 종료하며 미완성 출력 파일을 지운다.
- `store.rs`의 검증용 스키마는 다음과 같다. 제품 스키마는 로드맵 남은 작업 10에서 정한다.

```sql
CREATE TABLE lecture(id INTEGER PRIMARY KEY, course TEXT NOT NULL, recorded_on TEXT NOT NULL);
CREATE TABLE segment(id INTEGER PRIMARY KEY, lecture_id INTEGER NOT NULL, kind TEXT NOT NULL, body TEXT NOT NULL);
CREATE VIRTUAL TABLE segment_trigram USING fts5(body, tokenize='trigram', content='segment', content_rowid='id');
CREATE VIRTUAL TABLE segment_unicode USING fts5(body, tokenize='unicode61', content='segment', content_rowid='id');
```

- `search.rs`는 세 방식을 같은 입력·같은 상한(20건)으로 질의하고 결과 id와 걸린 시간을 돌려준다.
- **Tauri 명령:** `start_inference()`, `inference_status()`, `run_draft(text)`, `cancel_draft()`, `run_transcribe(path)`, `cancel_transcribe()`, `stop_inference()`, `search_notes(database, query, method, limit)`, `save_notion_token(value)`, `notion_token_saved()`, `delete_notion_token()`. 검색 명령은 하네스가 만들어 둔 DB 경로를 인자로 받는다. 코퍼스 생성처럼 오래 걸리는 작업은 화면 명령으로 만들지 않고 하네스에서만 실행한다.
- **화면:** 1차 녹음 탭 옆에 추론·검색·자격 증명 탭을 더한다. 각 탭은 버튼과 상태 표시, 기록 목록만 둔다.

## 6. 검증 절차

전원은 AC·"최고 성능"으로 두고 전원 모드·배경 부하를 기록한다. 사람이 해야 하는 조작은 없다.

1. **사전 확인** — `sqlite_version()`과 trigram 테이블 생성으로 FTS5를 확인한다. 여기서 막히면 9절의 대안으로 넘어간다.
2. **③ 추론 프로세스** — 서버를 0009 설정으로 띄워 준비 시간을 잰다. 토큰 없음·틀린 토큰·올바른 토큰 세 요청의 응답 코드를 확인하고, 기기의 LAN 주소로 같은 포트에 연결해 거부되는지 본다. 300토큰 생성 요청을 중간에 취소하고 이어서 같은 서버에 정상 요청을 보낸다. 30초 조각을 전사하고, 같은 전사를 중간에 취소해 자식 종료와 잔여 파일을 확인한다. 서버를 밖에서 강제 종료해 상태 전환과 재시작 복구를 본다. 마지막으로 하네스를 `taskkill /F`로 죽이고 남은 프로세스를 센다. 메모리는 시작·요청 중·정지 후 3회 기록한다.
3. **④ 검색** — FLEURS 문장에 강의별 고유 용어를 섞어 코퍼스를 만들고 세 방식으로 색인한다. 질의는 4절 ④ 표의 다섯 종류를 코퍼스에서 자동으로 뽑는다. 각 질의를 10회 실행해 지연을 기록하고, 본문 대조로 만든 정답과 비교해 재현율·정확도를 잰다. unicode61은 접두 질의(`"어간"*`)도 함께 잰다.
4. **⑤ 자격 증명** — 저장→조회→삭제→재조회를 하고, 하네스를 다시 실행해 지속을 확인한다. 로그·설정·DB에서 토큰 문자열을 검색하고 `cmdkey /list`로 항목이 사라졌는지 본다.

## 7. 자동 테스트

모델과 서버가 없어도 통과해야 한다. `cd app/src-tauri && cargo test`로 실행한다.

- `process.rs`: 실제 자식(`ping -n`)을 Job Object에 넣고, 정지 요청과 핸들 해제 뒤 프로세스가 사라지는지 확인한다.
- `llm.rs`: 요청 함수를 주입해 401·타임아웃·취소 경로를 가짜 응답으로 검사한다. 준비 대기 로직은 가짜 시계로 시험한다.
- `stt.rs`: `whisper-cli` 자리에 짧은 명령을 넣어 성공·실패·취소 경로를 확인한다.
- `store.rs`·`search.rs`: 문장 20개짜리 작은 코퍼스로 색인과 세 방식 질의를 그대로 시험한다. SQLite는 동봉이라 장치가 필요 없다.
- `secrets.rs`: `dev.justaclick.test/notion` 항목으로 저장·조회·삭제를 시험하고 끝에 지운다. 사용자의 다른 자격 증명은 읽지 않는다.
- 실제 모델·서버를 쓰는 검사는 `#[ignore]`로 두고 `cargo test -- --ignored`에서만 돌린다.
- 프런트엔드는 `npm run typecheck`만 확인한다.

## 8. 기록과 오류 처리

- 토큰은 환경 변수로만 자식에 넘기고 명령줄과 로그에 남기지 않는다. 앱 로그에는 자식 로그의 마지막 5줄을 경로를 가려 남긴다.
- 서버 포트는 0번 바인딩으로 빈 포트를 확보해 지정하고 `127.0.0.1`에만 연다.
- 생성 취소는 프로세스 종료가 아니라 HTTP 요청 중단으로 처리해 서버를 살려 둔다. 전사 취소는 자식 종료로 처리한다.
- 코퍼스와 DB는 `artifacts/app-search/`에, 자식 로그는 `artifacts/`에 두고 커밋하지 않는다.
- 자식 시작 실패, 준비 시간 초과, 인증 실패, 디스크 쓰기 실패는 상태와 화면에 원인을 남긴다. 실패해도 이미 만든 결과 파일은 지우지 않는다.
- 검증 결과는 `docs/validation/<날짜>-app-stack-2.md`에 쓰고, 판정과 라이브러리 버전·라이선스는 결정 0007 3절에 덧붙인다. 로드맵 남은 작업 7과 README도 함께 갱신한다.

## 9. 실패 시 대안

- trigram이 없거나 느리면 unicode61에 접두사 색인(`prefix='2 3'`)을 더해 비교하고, 그래도 기준을 못 넘으면 `LIKE` 폴백과 검색 범위 축소(과목·제목·노트만)를 기록한다.
- Job Object를 쓸 수 없으면 앱 시작 시 남은 자식을 찾아 정리하는 경로를 대안으로 남긴다.
- 자격 증명 관리자 접근이 막히면 DPAPI로 암호화한 파일 저장을 대안으로 기록한다.
- 생성 취소가 서버를 불안정하게 만들면 요청마다 프로세스를 다시 띄우는 방식을 비용과 함께 기록한다.
- 어느 항목이든 실패하면 원인과 대안을 결정 0007에 남기고, 녹음·화면 기반이 흔들리는 수준이면 C# .NET 재검토를 다시 꺼낸다.

## 10. 후속 작업

- Windows 10 기기 확보 후 ③④⑤ 재확인.
- 제품 데이터 스키마와 마이그레이션 설계(로드맵 남은 작업 10). 이번 검증용 스키마는 근거 자료로만 쓴다.
