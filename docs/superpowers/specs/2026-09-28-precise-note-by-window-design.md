# 정밀 정리 설계: 창별로 읽고 앱이 합치기

- 날짜: 2026-09-28
- 상태: 사용자 승인 설계. 구현·검증 전
- 대상: [결정 0010](../../decisions/0010-lecture-note-contract.md) v2의 정밀 정리 경로, [0006](../../decisions/0006-lecture-first-product-scope.md)의 정밀 정리(SUM-07)
- 근거: [시간 재측정](../../validation/2026-09-26-lecture-contract-timing.md), [시간 재측정 2](../../validation/2026-09-27-lecture-contract-timing-2.md)

## 1. 문제

지금 정밀 정리는 전체 전사를 한 번에 읽고 노트 본문(`lecture-note-body-v1`: 주제·개념·예제·용어·복습)을 쓴다. 두 재측정의 10건에서 결과가 두 갈래로 나뉘었다.

| 갈래 | 건수 | 개념 | 출력 | 인용 범위 |
| --- | --- | --- | --- | --- |
| 짧음 | 6 | 4개(교착 상태, 교착 상태 조건, 은행원 알고리즘, 안전 상태) | 713~1,272토큰 | s2~s14뿐. 세마포어·탐지·회복·예방·회피가 모두 빠짐 |
| 김 | 4 | 13~20개(상한 20) | 2,557~3,546토큰 | 전 범위. 같은 이름 반복("교착 상태 회복" 2번 등), 복습·연습 문제·다음 시간 주제를 개념으로 씀 |

첫 네 개념은 10건이 모두 같았고, 그다음에 목록을 닫을지 이어 쓸지가 한 토큰에서 갈렸다. 같은 강의의 5분 노트(초안 입력)는 10건 모두 세 창을 고르게 담았다(5~9개). 즉 지금은 "정밀" 버전이 5분 노트보다 덜 완전하다. 또 첫 재측정에서는 정밀 정리의 `topic`이 36개 구간을 모두 인용해 잡담 기대치가 깨졌다.

실제 2~3시간 강의는 전체 전사가 컨텍스트 8,192토큰을 넘으므로, 한 번에 읽는 방식은 합성 강의에서만 가능하다.

## 2. 사용자 결정

| 질문 | 결정 |
| --- | --- |
| 구조 | 나눠 읽고 앱이 합친다. 마지막 호출은 주제·복습만 쓴다 |
| 읽는 단위 | 5분 창 하나. 녹음 중 초안과 같은 창 경계 |
| 겹치는 개념·용어 | 앱이 이름으로 합친다. 모델이 다시 쓰지 않는다 |

## 3. 흐름

1. **창 호출**(창마다 1회): 그 창의 전사를 읽고 개념·예제·용어를 쓴다. 인용할 수 있는 구간은 그 창의 구간뿐이다.
2. **앱 병합**: 창 순서대로 이어 붙이고, 같은 개념·용어를 합치고, 창을 넘는 똑같은 예제를 지운다.
3. **합성 호출**(1회): 합친 개념 목록(이름·설명·출처)을 읽고 주제와 복습을 쓴다. 인용할 수 있는 구간은 합친 노트가 이미 인용한 구간뿐이다.
4. **조립**: 공지·코드는 지금처럼 초안에서 합치고(`merge_notices`, `merge_code`), 결과를 기존 `lecture-note-v2`(`Note`)로 만든다.

5분 노트 경로(초안 → `lecture-note-body-v1`)는 바꾸지 않는다.

## 4. 계약

### 4.1 모델 출력

| 스키마 | 필드 | 개수 |
| --- | --- | --- |
| `lecture-precise-window-v1` | `concepts`(이름·설명·출처) | 0~8 |
| | `examples`(내용·출처) | 0~6 |
| | `terms`(한국어 용어·정의·영문 원어·출처) | 0~10 |
| `lecture-precise-synthesis-v1` | `topic`(내용·출처) | 1 |
| | `review`(내용·출처) | 0~10 |

- 항목 모양은 `lecture-note-body-v1`의 `concept`·`item`·`term`과 같다. 앱이 정하는 `term_en_source`는 모델이 쓰면 거부한다.
- llama-server가 키를 알파벳 순서로 생성하므로 창 호출은 concepts → examples → terms, 합성 호출은 review → topic 순서로 나온다. 주제가 복습 뒤에 나오는 것은 괜찮다.
- 창마다 상한을 두어 한 호출이 되풀이로 길어지는 것을 막는다. 노트 전체의 개수 상한은 두지 않는다(긴 강의는 개념이 20개를 넘을 수 있다).
- 개념이 0개인 창은 위반이 아니다(쉬는 시간·잡담 창). 요약에 기록한다.

### 4.2 검증과 정리

- 호출마다 기존 규칙을 그대로 쓴다: 잘림·문법·중복 키·구조·출처 오류·항목 수 초과는 위반이고 1회 재시도, 채움 항목·똑같은 반복·용어를 되풀이한 정의는 정리해 기록한다.
- 합성 호출은 `topic`이 필수이고 `review`는 비어도 된다.

### 4.3 앱 병합 규칙

- **이름 비교**: 앞뒤 공백을 지우고, 공백을 하나로 줄이고, 끝의 문장부호를 지우고, 영문자는 소문자로 바꾼 값이 같으면 같은 이름이다.
- **개념**: 먼저 나온 개념을 남긴다. 뒤 개념의 설명이 (공백 정리 후) 다르면 먼저 설명 뒤에 한 칸 띄워 덧붙인다. 출처는 합치고 순서를 유지하며 중복을 뺀다. `concept_merged`로 기록한다.
- **용어**: 같은 방식으로 합친다. 정의는 개념 설명과 같이 덧붙이고, `term_en`은 먼저 나온 값이 `null`이 아니면 그대로, `null`이면 뒤의 값을 쓴다. 병합 뒤 `term_en_source`를 합친 출처 기준으로 다시 정한다. `term_merged`로 기록한다.
- **예제**: 내용이 (공백 정리 후) 같으면 먼저 것을 남기고 출처를 합친다. `example_merged`로 기록한다.
- 병합은 새 문장을 만들지 않는다. 덧붙인 설명은 각각 자기 호출에서 출처 검사를 통과한 문장이다.

## 5. 앱 구성

- `schemas/lecture-precise-window-v1.json`, `schemas/lecture-precise-synthesis-v1.json`을 더하고 `contract.rs`의 스키마 목록에 넣는다.
- `lecture.rs`: `PreciseWindow`, `PreciseSynthesis` 타입, `validate_precise_window`, `validate_precise_synthesis`, 프롬프트 `precise_window_prompt`(`lecture-precise-window-prompt-v1`), `precise_synthesis_prompt`(`lecture-precise-synthesis-prompt-v1`).
- `lecture_merge.rs`: `merge_precise(windows) -> (개념, 예제, 용어, 기록)`, `synthesis_input(개념) -> 문자열`, `assemble_precise_note(병합 결과, 합성 결과, 초안) -> Accepted<Note>`.
- 기존 `note_body_prompt`·`validate_note_body`는 5분 노트용으로 남긴다.

## 6. 측정과 판정

- 조건: AC 전원·"최고 성능"·배터리 완충(충전 없음), 배경 CPU 부하 기록(OneDrive 등), 측정 중 절전 방지, 카운터 수집. 서버 설정은 v2와 같다.
- 하네스: 기존 `note_body_from_transcript` 단계를 `precise_window`(창 3회) + `precise_synthesis`(1회)로 바꾼다. 나머지(창 초안 3호출 × 3창, 5분 노트)는 그대로 두고 **5회** 반복한다.
- 비교 대상: 두 재측정의 정밀 정리 10건.

| 기준 | 채택 조건 |
| --- | --- |
| 창 포괄 | 5회 모두, 노트의 개념이 세 창 각각의 구간을 1개 이상 인용 |
| 같은 이름 | 병합 뒤 같은 이름의 개념·용어 0건 |
| 판정용 기대치 | 노트에 적용되는 기존 판정용 기대치가 5회 모두 통과 |
| 편차 | 개념 수의 최소·최대 차이가 기존(4~20)보다 작음. 참고 지표로 보고 |
| 호출 | 모든 호출 채택(재시도 포함) |

- 시간 목표는 없다(0006). 호출별 시간·출력 토큰을 기록하고, 창 수에 비례한다고 보고 2.5시간 강의(창 30개)의 정밀 정리 시간을 추정해 다시 요약 1시간 목표와 비교한다. 추정으로 표시한다.
- 참고: 짧음 갈래에서 빠졌던 개념(세마포어, 탐지, 회복, 예방, 회피)이 5회 모두 들어가는지 적는다.

## 7. 자동 테스트

- 두 스키마와 타입의 필드 일치, 배열 `maxItems`, 합성 호출 `topic` 필수.
- 창 호출 검증: 다른 창의 구간 인용 거부(생성 `enum`과 검증 모두), 개념 0개 허용, 앱 필드 거부.
- 병합: 이름 정규화(공백·끝 문장부호·영문 대소문자), 설명 덧붙임과 출처 합치기, 같은 설명은 덧붙이지 않음, 용어 `term_en` 선택과 `term_en_source` 재계산, 같은 예제 병합, 기록 경로.
- 합성 입력의 구간 제한: 합친 노트가 인용하지 않은 구간(잡담)은 `enum`에 없다.
- 조립: 공지·코드는 초안에서 합쳐지고 결과가 `Note`로 직렬화된다.

## 9. 한계

- "안전 상태"와 "안전한 상태"처럼 표현이 다르면 둘 다 남는다.
- 창 경계에 걸친 설명은 두 창에 나뉘어 들어갈 수 있다.
- 덧붙인 설명은 매끄럽지 않을 수 있다. 읽기 품질은 실제 강의 평가셋(작업 9)에서 본다.
- 합성 강의 1개(창 3개)로는 긴 강의의 병합 규모를 확인할 수 없다.
