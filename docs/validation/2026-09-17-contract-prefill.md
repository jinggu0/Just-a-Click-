# 회의 출력 계약 및 긴 입력 처리 진단

- 날짜: 2026-09-17
- 모델: 기존 Qwen3-8B Q5_K_M, llama.cpp b10994, Vulkan
- 범위: 회의 계약 검증, Flash Attention 요청 설정 비교, 입력 처리량 진단
- 상태: 담당자·기한 구조 개선 확인. 시간·의미 품질·장문 안정성의 출시 판정은 미통과

## 구현

회의 스키마와 로컬 검증을 추가했다. 모든 후속 작업에 owner·deadline이 필수이며 미언급 값은 null이어야 한다. 출처 ID를 실제 입력으로 제한하고, 명시된 값이 인용한 원문에 존재하는지 확인한다. 잘린 출력, 중복 JSON 키, 알 수 없는 필드·출처, 빠진 필드를 거부한다.

검증에 실패하면 `accepted-N.json`을 만들지 않는다. 원응답은 실패 분석용으로 남긴다. 이전 CPU 응답의 기한 누락과 ‘미정’이라는 실제 이름을 미정 상태와 혼동하지 않는 사례 등을 포함해 테스트 11개가 통과했다. 일반적인 의미 정확성은 문법·원문 등장 검사만으로 보장되지 않는다. [계약 결정](../decisions/0005-summary-contract.md).

## 측정 조건과 결과

기준 노트북·모델·16,384 컨텍스트·8스레드·seed 42를 유지했다. non-thinking을 `--reasoning off`로 설정하고 템플릿/입력 예산 확인과 로컬 검증·저장 시간을 측정에 포함했다. 다른 프로그램 부하·온도는 통제하지 않았다. 각 설정은 1회 진단이며 통계적으로 최적 설정을 판정하는 실험이 아니다.

엄격한 스키마를 프롬프트에도 제공하므로 입력은 926토큰, 출력은 329토큰이다. 이전 약한 JSON 시험(446/292토큰)과 직접 비교해 설정만의 효과로 해석하지 않는다.

| 요청 설정 | 준비 | 짧은 요약 요청~검증·저장 | 준비 포함 첫 요약 | 4,096토큰 입력 시험 | 8,192토큰 입력 시험 |
| --- | --- | --- | --- | --- | --- |
| Flash Attention auto, 기본 배치 | 23.91초 | 142.90초 | 166.81초 | 65.70초 | 미실시 |
| Flash Attention on, 기본 배치 | 18.44초 | 122.04초 | 140.48초 | 48.88초 | device lost 실패 |
| Flash Attention on, batch 512 / ubatch 128 | 13.79초 | 미실시 | 미실시 | 미실시 | 185.66초, 완료 |

처음 두 실행은 배치를 명시하지 않았고 해당 빌드 도움말의 기본값은 batch 2048 / ubatch 512다. 세 번째 실행은 512 / 128을 명시했다. 표의 Flash Attention은 요청한 옵션이며 auto가 실제로 어떤 경로를 선택했는지 별도 확인하지 않았다. 따라서 두 설정 차이가 관측된 시간 차이의 원인이라고 단정하지 않는다.

입력 시험은 반복 합성 텍스트의 정확한 토큰 배열을 제공하고 **1토큰만 생성**했다. 성공한 모든 시험에서 실제 prompt_n이 요청 수와 같고 truncated=false였다. 4시간 녹음, 다양한 장문 내용의 이해·통합 또는 요약 품질 시험은 아니다.

- auto 요약: 모델 내부 입력 처리 15.62초, 생성 127.12초.
- on 요약: 모델 내부 입력 처리 9.59초, 생성 112.32초.
- 작은 배치의 8,192토큰 시험: 모델 내부 입력 처리 185.61초, 약 44.14토큰/초.
- 출력 생성뿐 아니라 긴 입력 자체도 큰 병목이다. 출력 토큰을 무조건 줄이거나 원문을 생략하는 방식으로 목표를 충족시키지 않는다.

## 출력 검수

두 요약의 내용은 같았다. 지민 담당·기한 null, 로컬 보존, 해시 검사, 전사 제외 시간 목표, GPU 미측정 상태를 보존하고 잡담은 제외했다. 모든 후속 작업 항목에 owner·deadline 필드가 존재했고 GPU 미측정 상태는 open_questions로 이동했다. 이번 합성 사례의 6개 자동 회귀 검사는 모두 통과했다.

**남은 오류:** SHA-256 정책과 2분 성능 목표를 후속 작업으로 분류했다. 이 분류 문제는 현재 자동 회귀 검사에서 검출하지 않으며 수동 검수로 확인했다. 따라서 ‘계약 통과’를 ‘요약 품질 완성’으로 표시하지 않는다. 분류 라벨 검수와 정책/업무 구분 예시를 추가해야 한다.

## GPU 실패와 복구

기본 배치의 8,192토큰 실행에서 HTTP 500과 `vk::Device::getFenceStatus: ErrorDeviceLost`가 발생했다. 이 실행은 failed로 기록했고 서버 프로세스를 종료했다. 로그의 토큰 진행 표시를 완료로 간주하지 않았다.

Windows 드라이버·TDR·레지스트리는 변경하지 않았다. 동일한 8,192토큰을 새 프로세스에서 batch 512 / ubatch 128로 재시험했으며 1회 완료했다. 이 결과는 작은 배치가 모든 device lost의 원인을 해결한다는 증거가 아니다. 해당 설정은 후속 안정성 검증 후보로 유지하고 제품 기본값으로 승격하지 않는다.

실패 보고는 [on 결과](../../evaluation/results/2026-09-17-contract-on.json)에 남겼다. 최초 실패 당시 도구가 미완료 probe 항목을 기록하지 못한 부분은 서버 로그에서 확인한 실패 문맥을 명시적으로 덧붙였다. 도구도 수정하여 이후에는 실패한 probe의 입력 수·시간·HTTP 오류 내용을 보고서에 남기게 했다.

## 판정과 다음 순서

1. **완료:** 회의 구조 계약·거부 동작·회귀 테스트, 실제 GPU 요약 2건 검수, 4,096토큰 2회 및 작은 배치 8,192토큰 1회 처리 확인.
2. **미달:** 짧은 요약조차 준비 포함 120초를 넘었고, 작은 배치의 8,192토큰 입력 시험만 약 186초다. 4시간·120초 목표와 출시 품질 플래그는 계속 false다.
3. **다음:** Intel SYCL 등 가속 경로와 작은 배치의 안정성을 비교하고, 정책/업무 분류 회귀 사례를 보강한다. 선택 모델·시간 목표를 임의로 변경하지 않는다.
4. 실제 음성 STT, 다양한 장문 요약, 메모리 최대치 및 Windows 10 검증은 별도 남아 있다.
