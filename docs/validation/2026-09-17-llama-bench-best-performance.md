# llama-bench 재측정: 최고 성능 전원 모드

- 날짜: 2026-09-17
- 모델·런타임: Qwen3-8B Q5_K_M, llama.cpp b10994 (CPU·Vulkan)
- 범위: [첫 측정](2026-09-17-llama-bench.md)과 같은 합성 토큰 처리량 측정과 합성 회의 프롬프트의 서버 비교를 Windows 전원 모드 "최고 성능"에서 반복. 실제 강의·STT·앱 지연시간·요약 품질 시험이 아님
- 결과 파일: [처리량](../../evaluation/results/2026-09-17-llama-bench-all-best-performance.json), [제약 비교: none](../../evaluation/results/2026-09-17-constraint-none-best-performance.json)·[json](../../evaluation/results/2026-09-17-constraint-json-best-performance.json)·[schema](../../evaluation/results/2026-09-17-constraint-schema-best-performance.json), [추정](../../evaluation/results/2026-09-17-feasibility-best-performance.json)

## 요약

- 전원 모드만 "최고 성능"으로 바꾸자 Vulkan 생성 속도가 깊이 0 기준 약 3.8~4.0 → 12.9~13.9 tok/s로 약 3.5배 빨라졌다. GPU 전력(RAPL PP1)도 중앙값 약 2.7W → 9.6W로 비슷한 비율로 늘었다.
- 서버 출력 제약별 생성 속도는 none 13.84, json 13.64, schema 14.10 tok/s였다. 이번에도 스키마 제약에 의한 감속은 관측되지 않았다.
- 1차 판정(추정)은 **feasible_estimate**다. 녹음 종료 후 89~93초(목표 300초), 3시간 강의 다시 요약 924~986초(목표 3,600초), 녹음 중 LLM 점유율 0.08~0.09로 여유가 크다. 보수적 민감도 계산에서도 모두 목표 안이었다.
- 반면 온도가 크게 올랐다(Vulkan 측정 중 중앙값 81°C·최대 93°C, CPU 측정 중 최대 97°C). 같은 기기라도 전원 모드에 따라 판정이 바뀌므로, 배터리 사용·장시간 녹음 조건은 따로 검증해야 한다.

## 판정과 다음 결정

"최고 성능" 전원 모드의 AC 연결 조건에서 녹음 종료 후 5분·다시 요약 1시간 목표는 여유 있게 가능하다고 추정된다. "최고의 전원 효율성"에서는 미달로 추정됐으므로, 목표 달성은 기기의 전원 상태에 크게 의존한다. 이 판정은 원시 처리량과 가정으로 계산한 추정이며 앱 지연시간이나 출시 품질의 판정이 아니다.

모델과 시간 목표는 바꾸지 않는다. 다음 검증에서 확인할 사항은 다음과 같다.

1. 로컬 STT 후보 측정과 녹음 중 STT·LLM 동시 실행의 속도·메모리를 전원 모드별로 측정한다.
2. 배터리 사용 시의 처리량, 2~3시간 연속 처리의 배터리 소모·온도·팬 소음을 측정한다. 이번 측정의 최고 온도는 97°C였다.
3. 앱이 실행 시 전원 모드·전원 연결 상태를 기록하고, 시간 목표 판정과 함께 표시하는 방식을 설계한다. 전원 설정 변경은 사용자에게 맡긴다.
4. 입력 처리 속도가 깊이에 따라 거꾸로 늘어난 원인과, 추정기와 서버 실측의 약 16% 차이를 확인한다.

## 한계

- 합성 토큰과 합성 회의 프롬프트 1건만 사용했고, 실제 강의 전사문·STT·앱 경로는 포함하지 않았다.
- 기준 기기 1대, 조건별 3회, 1회 실행이다. 배경 부하(탐색기·검색 색인·VMware)와 온도를 통제하지 않았다.
- 전원 모드 비교는 통제 실험이 아니며 배터리 사용 조건은 측정하지 않았다.
- 입력 처리 속도의 깊이별 경향이 첫 측정과 반대여서 곡선 해석에 불확실성이 있다. 민감도 계산으로 판정 영향만 확인했다.
- 작업량은 가정이며 구간 초안·최종 통합의 실제 출력 길이와 품질은 측정하지 않았다.
