## 1. 요약

**v2 계약은 품질 기준을 통과해 채택한다. 시간 판정은 보류한다.** 호출 75건이 재시도 없이 모두 채택됐고, 판정용 기대치 7개가 5회 모두 통과했다. v1에서 실패했던 것들이 모두 해결됐다: 모호한 기한, 취소된 퀴즈, 쉬는 시간 발언의 가짜 공지, 코드 누락. 공지는 다섯 노트 모두 시험 날짜·범위 원문, 퀴즈 취소, 과제를 정확히 담았고, 코드는 `chmod 755 run.sh`·`gcc -o banker banker.c`를 15/15 원문 그대로 잡았다.

시간은 기준을 넘었다. 창 15개 중 5개가 150초를 넘었고(최대 212초), 녹음 종료 후 추정은 5회 모두 300초를 넘었다(429~622초). 다만 이번 측정의 생성 속도는 초당 6.7토큰(중앙값)으로, 측정 직전에 같은 코드로 한 시험(12.9토큰)의 절반이었다. 출력 토큰 수는 비슷했으므로 시간 초과는 속도 저하 때문이다. 원인은 확인하지 못했다. 시험 때 속도로 환산하면 창 약 76초, 녹음 종료 후 약 240초로 기준 안이다(추정).

| v2 시험(1회, 측정 직전) | 12.9 | 처음부터 끝까지 12~13 |

**시험 때 속도로 환산한 추정.** 창 하나의 출력이 약 880토큰이므로 초당 12.9토큰이면 생성에 약 68초, 입력 처리 세 번에 약 8초가 들어 창 약 76초가 된다. 실제로 시험에서는 66~69초였다. 5분 노트 본문은 약 1,070토큰이라 약 90초가 걸리고, 녹음 종료 후 추정은 약 240초다. 이 값은 추정이며 판정에 쓰지 않는다.

## 4. 원응답에서 본 남은 문제

| 문제 | 관찰 |
| --- | --- |
| 코드 정밀도 | 모든 노트에 코드가 아닌 항목이 3~5개 들어갔다("Banker's algorithm", "C", "wait", "signal", "kill"). 영문자가 있어 앱의 정리를 통과한다. "wait"·"signal"은 세마포어 연산 이름이라 경계에 있다 |
| 잘못된 영문 보강 | "타조 알고리즘=Duck algorithm", "점유 대기=Wait-die"처럼 틀린 원어가 나왔다. 앱이 "모델 보강"으로 표시하지만 내용은 틀렸다 |
| 용어 이름 반복 | 정밀 정리에서 같은 용어가 여러 번 나왔다(예: "교착 상태 조건" 4번). 정리는 정의 문장만 비교하므로 이름 반복은 남는다 |
| 정밀 정리의 반복·길이 | 노트당 평균 8건의 똑같은 반복을 정리했고, 출력이 최대 3,497토큰·840초였다(시간 목표 없음) |
| 복습 항목 | 노트당 0~7개로 적었다 |

## 5. 발견한 제약

1. **llama-server는 스키마 순서와 상관없이 객체의 키를 알파벳 순서로 생성한다.** 따라서 필드 이름이 생성 순서를 정한다. 참·거짓 `cancelled`는 늘 내용보다 먼저 정해져 `false`로 나왔고, 알파벳 순서상 내용 뒤에 오는 `status`로 바꾸자 해결됐다. 판단 필드는 근거 필드 뒤에 오도록 이름을 짓는다.
2. **호출마다 배열 하나면 쏠림이 사라진다.** 요점·공지·코드가 모두 채워졌다. v1의 쏠림은 알파벳 순서상 마지막인 `points`로 간 것이었다(v1 보고서 정정).
3. **명령어가 없는 창에서도 코드 호출은 무언가를 채운다.** 한글만 있는 항목은 결정적으로 지울 수 있지만, 영문 개념 이름은 남는다.
4. **생성 속도가 같은 조건 표기 아래에서도 절반으로 떨어질 수 있다.** 시간 판정에는 전력·온도 기록과 전원 상태의 통제가 필요하다.

## 7. 한계

- 합성 강의 1개, 5회 반복이다. 기대치는 fixture 전용 회귀 검사이며, 함정 두 개와 v2 규칙 일부(한글만 있는 코드 삭제, `status` 필드)는 같은 fixture로 시험한 뒤 정했으므로 과적합 가능성이 있다.
