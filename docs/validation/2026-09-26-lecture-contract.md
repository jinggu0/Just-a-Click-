# 강의 노트 출력 계약 실측

- 날짜: 2026-09-25 22:29 ~ 2026-09-26 00:06(5회 측정)
- 범위: [로드맵](../ROADMAP.md) M0 남은 작업 8. 구간 초안(`lecture-draft-v1`)과 강의 노트(`lecture-note-v1`) 계약을 앱(Rust)에 구현하고, 직접 작성한 합성 강의로 Qwen3-8B의 계약 준수와 출력 토큰·시간을 쟀다
- 조건: 시작과 끝 모두 AC 전원·Windows 전원 모드 "최고 성능"(배터리 58%→86%), 경쟁 프로세스 없음. 측정 중 절전을 막았다
- 구성: llama.cpp `b10994` Vulkan `llama-server`, Qwen3-8B Q5_K_M, 컨텍스트 8,192, `-np 1`, `--cache-ram 0`, `-ngl 99`, 2스레드, `--jinja --reasoning off`, 온도 0.2, 출력 한도 초안 2,048·노트 4,096토큰, 프롬프트 `lecture-draft-prompt-v2`·`lecture-note-prompt-v2`
- 입력: [합성 강의](../../evaluation/fixtures/lecture-synthetic-v1.json)(운영체제 교착 상태 15분, 5분 창 3개·구간 36개, 함정 포함)
- 결과 파일: 원응답·호출별 기록·프롬프트·서버 로그는 `artifacts/lecture-contract/run/`에 두고 커밋하지 않는다
- 설계·계획: [계약 설계](../superpowers/specs/2026-09-25-lecture-note-contract-design.md), [실행 계획](../superpowers/plans/2026-09-25-lecture-note-contract.md), 결정 [0010](../decisions/0010-lecture-note-contract.md)

## 1. 요약

**계약 구조와 검증기는 설계대로 동작했지만, 모델의 계약 준수가 부족해 채택을 보류한다.** 25건 응답이 모두 구조·출처 검사를 통과해 채택됐고(재시도 1회), 초안 15건은 첫 시도에 정리할 것도 없이 깨끗했다. 그러나 설계의 채택 기준인 창작 방지 기대치 가운데 "모호한 기한은 `null`"이 정밀 정리 5건 중 4건에서 깨졌다.

자동 기대치가 잡지 못한 체계적 문제도 컸다. 초안 15건 모두 `concepts`·`examples`·`code`가 비고 내용이 `points`로 몰렸으며, 노트 10건에도 코드가 한 건도 없었다. 취소된 퀴즈를 날짜가 붙은 시험으로 분류했고, "잠깐 쉬었다가"에서 가짜 과제를 만들었으며, 같은 공지를 최대 4번 되풀이했다.

시간도 가정을 넘었다. 초안 출력은 최대 557토큰으로 결정 0009의 300토큰 가정의 1.9배였다. 초안으로 노트 전체를 다시 쓰는 5분 노트 경로는 녹음 종료 후 추정이 회차별 236~1,563초로, 5회 중 2회가 300초를 넘었다.

## 2. 계약

설계 4절을 요약한다. 합성 강의로 두 번 시험한 뒤 사용자와 정한 분담에 따라 **모델은 내용만 쓰고, 전사로 정할 수 있는 것은 앱이 정한다**.

| 구분 | 내용 |
| --- | --- |
| 초안 | 요점 1~8, 개념 이름 0~8, 예제 0~6, 코드 0~8, 공지 0~5. 창 범위는 앱이 채운다 |
| 노트 | 주제, 개념 1~20, 예제 0~15, 용어 0~20, 공지 0~10, 코드 0~20, 복습 0~10 |
| 앱이 채우는 값 | 코드가 인용 구간에 그대로 있는지(`from_transcript`), 영문 원어가 인용 구간에 있는지(`term_en_source`) |
| 정리(기록) | 인용 구간에 없는 날짜·범위와 채움 문자열을 `null`로, 채움 항목·똑같은 반복·정의가 용어를 되풀이한 용어를 삭제 |
| 거부(1회 재시도) | 잘림, 문법·구조 오류, 중복 키, 앱이 정하는 필드를 모델이 쓴 경우, 출처 오류, 필수 섹션 비움, 항목 수 초과 |

## 3. 결과

### 3.1 채택과 토큰·시간

| 단계 | 호출 | 첫 시도 깨끗함 | 첫 시도 유효 | 채택 | 재시도 | 출력 토큰 중앙값 / 최대 | 시간 중앙값 / 최대 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 구간 초안 | 15 | 15 | 15 | 15 | 0 | 444 / 557 | 47.0 / 107.3초 |
| 5분 노트(초안 입력) | 5 | 2 | 4 | 5 | 1 | 1,548 / 4,096 | 190.5 / 1,348.7초 |
| 정밀 정리(전체 전사) | 5 | 0 | 5 | 5 | 0 | 3,462 / 3,945 | 481.0 / 780.0초 |

"깨끗함"은 위반도 정리도 없었다는 뜻이고 "유효"는 정리 후 위반이 없었다는 뜻이다. 5분 노트의 재시도 1회는 4,096토큰 한도에서 잘린 응답이었고, 재시도까지 합쳐 1,348.7초가 걸렸다.

정리 횟수는 5분 노트에서 똑같은 반복 3건, 정밀 정리에서 똑같은 반복 103건(노트당 평균 21건)과 확인할 수 없는 날짜·범위 17건이었다.

### 3.2 기대치

| 기대치 | 채택 판정용 | 통과 / 해당 |
| --- | --- | --- |
| 잡담 제외 | 예 | 25 / 25 |
| 시험 날짜·범위 원문 유지 | 예 | 15 / 15 |
| 취소된 퀴즈를 공지하지 않음 | 예 | 15 / 15 |
| 배점 미생성 | 예 | 25 / 25 |
| **모호한 기한은 `null`** | 예 | **11 / 15** |
| 과제 포착 | 아니오 | 12 / 15 |
| 라틴 문자 명령어 원문 유지 | 아니오 | **0 / 15** |
| 말하지 않은 영문 원어를 모델 보강으로 표시 | 아니오 | 9 / 9 |
| 발음 명령어 복원 표시, 말한 영문 원어 표시 | 아니오 | 해당 없음(해당 항목이 한 번도 나오지 않았다) |

"모호한 기한은 `null`" 실패 4건은 모두 정밀 정리에서 나왔다. 과제 공지의 `date_text`에 "다음 주쯤", "다음 주", "게시판에 따로 공지할게요"를 넣었다. 모두 전사에 그대로 있는 문자열이라 원문 대조로는 걸러지지 않는다.

### 3.3 자동 기대치가 잡지 못한 문제

원응답을 직접 확인했다.

| 문제 | 관찰 |
| --- | --- |
| 섹션 쏠림 | 초안 15건 모두 `concepts`·`examples`·`code`가 비었다. 내용은 `points`(4~8개)로만 갔다 |
| 코드 누락 | 초안·노트 25건 어디에도 코드 항목이 없었다. 실습 창(`chmod 755 run.sh`, `gcc -o banker banker.c`, 발음 전사 "피에스 에이유엑스")도 요점으로만 남았다 |
| 취소된 일정의 분류 | 취소된 퀴즈를 `exam`으로 분류하고 `date_text`에 "다음 주 수요일"을 넣었다. 내용에 "취소"가 있어 기대치는 통과했지만 화면에는 날짜가 붙은 시험처럼 보인다 |
| 없는 과제 생성 | 정밀 정리 한 건이 "잠깐 쉬었다가 실습실 환경으로"에서 `date_text: "잠깐"`인 과제를 6번 만들었다 |
| 공지 반복 | 같은 공지를 초안에서 최대 3번, 노트에서 최대 4번 되풀이했다. 공지는 정리 대상이 아니어서 그대로 남는다 |
| 잘못된 영문 보강 | "타조 알고리즘"의 원어를 "Dijkstra's algorithm"으로 적었다. 앱이 모델 보강으로 표시하지만 내용이 틀렸다. 강의에서 말한 "deadlock"은 한 번도 원어로 적히지 않았다 |
| 전사 복사 | 공지 내용이 전사 문장을 거의 그대로 옮겼다 |

## 4. 시간 영향

| 항목 | 값 | 기준 |
| --- | --- | --- |
| 초안 출력 토큰 최대 | 557 | 결정 0009 가정 300 |
| 초안 시간 최대 | 107.3초 | 결정 0009 창 초안 판정 150초 이내 |
| 녹음 종료 후 추정(2 × 최대 초안 + 5분 노트), 회차별 | 236, 240, 289, 1,563, 619초 | 300초 이내 |

초안은 가정보다 길지만 창 안에서 처리할 수 있다. 문제는 5분 노트다. 이번 하네스는 초안을 입력으로 **모델이 노트 전체를 다시 쓰는** 방식이라 출력이 1,548~4,096토큰에 이르렀다. [결정 0006](../decisions/0006-lecture-first-product-scope.md)과 [LLM 지역화](../LLM-SPECIALIZATION.md)는 5분 노트를 "앱 코드 병합 위주"로 정했으므로, 병합은 앱이 하고 모델은 주제·복습처럼 합성이 필요한 부분만 쓰는 구성이 필요하다. 이는 파이프라인 설계(작업 4)의 몫이다. 목표를 맞추려고 입력을 줄이지는 않는다.

정밀 정리는 시간 목표가 없지만 중앙값 481초·최대 780초였고 출력이 4,096토큰 한도에 가까웠다(최대 3,945).

## 5. 발견한 제약

1. **한 번에 여러 섹션을 채우게 하면 한 섹션으로 쏠린다.** 초안에서 Qwen3-8B는 `points`만 채우고 나머지 배열을 비웠다. (2026-09-26 정정: 처음에는 "첫 배열로 쏠린다"고 추정했지만, v2 시험에서 llama-server가 스키마 순서와 상관없이 키를 알파벳 순서로 생성한다는 것을 확인했다. v1 초안의 생성 순서는 `code`, `concepts`, `examples`, `notices`, `points`였으므로 앞의 세 배열이 비고 마지막 `points`로 쏠린 것이다.) 섹션을 나눈 계약만으로는 개념·예제·코드가 모이지 않는다.
2. **모델이 반복해서 틀리는 값은 앱이 정해야 한다.** 영문 원어의 출처와 창 범위를 앱이 채우자 해당 오류가 더 나오지 않았다. 코드의 원문 여부는 코드 항목이 나오지 않아 확인하지 못했다. 날짜 자리의 "없음"도 정리로 처리됐다.
3. **원문 대조는 모호함을 걸러내지 못한다.** "다음 주쯤", "잠깐"처럼 전사에 그대로 있지만 날짜가 아닌 표현이 날짜로 들어갔다. 원문 대조만으로는 판정할 수 없는 의미 문제다.
4. **노트 전체를 다시 쓰면 반복과 길이가 폭주한다.** 정밀 정리는 노트당 평균 21건의 똑같은 반복을 만들었고 한도에 가까웠다.
5. **문법 제약이 있어도 초안은 안정적이다.** 초안 15건은 모두 첫 시도에 깨끗했고 최대 107.3초였다.

## 6. 판정과 다음 결정

| 항목 | 판정 |
| --- | --- |
| 계약 구조·검증기 | 동작. 최종 구조·출처 위반 0건, 영문 원어 표시·창 범위·정리가 설계대로 작동(코드 표시는 항목이 없어 미확인) |
| 계약 채택(설계 7절 기준) | **미달.** 창작 방지 기대치 중 모호한 기한이 정밀 정리 4/5에서 실패 |
| 모델 준수 | **부족.** 섹션 쏠림, 코드 전량 누락, 취소 일정 분류, 없는 과제 생성, 공지 반복 |
| 시간 | 초안은 창 안(최대 107.3초). 5분 노트 경로는 5회 중 2회가 300초 초과 |

로드맵 남은 작업 8은 완료로 두지 않는다. 계약 v1의 구조(섹션, 앱이 정하는 값, 정리 규칙)는 다음 시도의 기준으로 유지하고, 다음 가운데 무엇을 할지 사용자와 정한다.

1. **작업 나누기:** 초안은 요점과 근거만 쓰게 하고, 공지·코드는 짧은 전용 호출이나 규칙 기반 후보 추출(라틴 문자 명령어는 규칙으로 찾을 수 있다)로 따로 모은다.
2. **5분 노트를 앱 병합으로:** 결정 0006대로 초안 병합은 앱이 하고 모델은 합성 부분만 쓴다(작업 4와 함께).
3. **정리 규칙 보강:** 같은 공지의 반복 제거처럼 결정적인 정리를 더한다. 이번 결과를 보고 규칙을 더하는 것이므로 다시 측정해 확인한다.
4. **모델 개량:** 위 구조 변경 뒤에도 부족하면 [LLM 지역화](../LLM-SPECIALIZATION.md)의 지도 미세조정 근거로 쓴다.

## 7. 한계

- 합성 강의 1개, 5회 반복이다. 기대치는 이 fixture 전용 회귀 검사이며 다른 강의의 품질 점수가 아니다.
- 의미 충실성은 자동 채점하지 않았다. 3.3절의 관찰은 원응답을 직접 읽은 결과다.
- 실제 강의 녹음·전사 오류, 2~3시간 분량, RAM 16GB 기기는 확인하지 않았다.
- 계약과 규칙 일부(필수 섹션, 항목 수 상한, 앱의 값 채움과 정리)는 같은 합성 강의로 두 번 시험한 뒤 정했다. 이번 5회 측정은 그 뒤에 따로 실행한 결과지만, 같은 fixture라 과적합 가능성이 남는다.
- 계획 작성 중 한동안 노트북이 배터리 상태였다. 그때의 시험 실행은 동작 확인에만 쓰고 시간 판정에는 쓰지 않았다.
